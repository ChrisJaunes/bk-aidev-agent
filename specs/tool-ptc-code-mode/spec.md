# 工具 PTC：模型通过 code mode 调用工具

- 变更名: tool-ptc-code-mode
- 工作分支: feature/tool-ptc-code-mode
- 类型: 功能
- 仓库: git@github.com:ChrisJaunes/bk-aidev-agent.git
- 执行顺序: 无

## 范围

在 Agent SDK 既有执行链路上新增一种工具使用模式：模型不再逐轮发起 tool call，而是**写一段代码**编排工具调用，代码在运行时沙箱内执行，代码内通过同步函数调用使用已装配的工具。本变更交付该链路的可运行能力、与之配套的事件与异常语义，以及一份收益测算方案（不含评测代码）。

1. 开关：`ExecuteKwargs` 新增 `tool_use_mode`，取值 `function_call`（缺省）/ `code_mode`，随既有 `execute_kwargs` 透传链路生效，不新增接口。
2. 模型可见工具集合：code mode 下模型只绑定一个代码执行工具；其余已装配工具以**精简清单说明**（名称、用途、参数要点）注入提示，不再以完整 JSON Schema 常驻。
3. 代码执行：模型生成的代码在该会话所选运行时后端的沙箱内执行；代码内的工具函数走现有工具执行链路（超时、结果脱敏、结果截断、MCP 代理、审批包装），与 function calling 共用同一套工具实现。
4. 上下文回填：一轮只把「代码」与「执行输出」两段回填模型；代码内每次工具调用的入参与结果**不进模型上下文**（这是本变更的 token 收益来源）。
5. 事件与展示：代码内每次工具调用都必须产生一对 `TOOL_CALL_START` / `TOOL_CALL_ARGS` / `TOOL_CALL_END`，复用现有 AG-UI 事件与 chat-x 渲染；前端零改动。
6. 中断类工具排除：ask 类工具与带生效审批配置的工具不进代码环境、不进精简清单；命令级审批在 code mode 下不发起，灰名单命令 fail-closed。判定口径与兄弟变更 `tool-loading-mode`（`mode=dontInterrupt`）同源，两模式叠加取交集。
7. 异常与重试：代码执行报错、工具失败、执行超时三类异常都回传模型，模型可修正后重试，重试上限可配置。
8. 运行时覆盖：`local`、`bubblewrap`（`sandbox_policy` 生效时 local 的既有替代实现）、`agent_run`（E2B）、`paas` 四类 runtime 都必须支持 code mode，能力面一致。
9. A2A 子 Agent 继承父 Agent 的 `tool_use_mode`。
10. 收益测算方案：交付《code mode 收益测算方案》文档（任务集、指标口径、对照方法、采样口径、判据），不实现评测代码、不产出实测数据。

## 非目标

- 不写评测代码、不建评测框架、不产出 token / 轮次 / 耗时 / 成功率的实测数据或对比报告；本期只交付测算方案。
- 不改前端任何代码：`src/frontend/ai-blueking/packages/chat-x` 及其它 UI 零 diff；不新增 AG-UI 事件类型、不改事件字段。
- 不改默认（`function_call`）路径的工具集合、提示词、事件序列、审批链路与会话数据结构。
- 不做 code mode 与工具延迟加载（lazy tools / tool search）的叠加优化；两者本期互不感知。
- 不引入新的代码执行语言运行时：本期只支持 Python，不提供 JS / TS / shell 代码块模式。
- 不做跨轮持久内核（persistent kernel / REPL 会话）：每次代码执行独立，内存状态不跨轮保留。
- 不在 code mode 内承载任何人工中断（ask / 工具级审批 / 命令级审批）：需要人工介入的调用方应选用 `function_call`。
- 不为外部 MCP 工具或第三方 `StructuredTool` 推断「是否会中断」；判定口径与 `tool-loading-mode` 完全一致，不新增工具名单配置项。
- 不改沙箱隔离级别、命令黑名单 / 白名单 / 语法规则等既有防护档位；不放宽文件可见范围。
- 不在平台配置界面新增开关，不改平台 `agent_info` 配置键，不新增 HTTP 路由。
- 不做 code mode 下的工具结果缓存、去重与跨调用复用。

## 跨仓边界

- 本任务只有 `bk-aidev-agent` 一个业务仓，无跨仓接口、无跨仓依赖、无跨仓执行顺序。
- `chat-x` 前端在本仓 monorepo 内（`src/frontend/ai-blueking/packages/chat-x`），但本期零改动：code mode 产生的内层工具调用事件必须落在既有事件字段集合内，靠同一套 ToolCall 渲染即可显示。
- 平台侧（`bk-aidev` 后端、内置插件、企微渠道）不在本仓，也不需要改造：`tool_use_mode` 是 `execute_kwargs` 的新增可选字段，既有透传链路原样带到 SDK。
- 与兄弟变更 `tool-loading-mode`（`ExecuteKwargs.mode`，分支 `feature/tool-lazy-loading`，基线 `develop` 尚未合入）的关系：**口径对齐、可叠加、合入顺序互不阻塞**。两个模式可同时使用，最终可调用集合取交集；`mode` 的过滤实现（`filter_tools_by_loading_mode` / `command_approval_allowed`）未合入时，code mode 必须自带等价过滤，不得因缺该实现而静默放行中断类工具或命令级审批。

## 用户故事

- 作为无人值守的 API 调用方，我希望模型写一段代码一次编排多个工具调用，这样多步任务的请求轮次与 token 消耗不随步骤数线性膨胀。
- 作为无人值守的 API 调用方，我希望 code mode 下不会有任何人工中断（提问、审批），自动化任务不会挂起等一个不会到来的答案。
- 作为平台研发，我希望用同一个请求参数在两种模式间切换，这样可以在不改调用方代码的情况下做收益对比。
- 作为 chat-x 使用者，我希望 code mode 里发生的工具调用跟现在一样能看见、能展开，不因为换了执行方式而「消失」。
- 作为验收方，我希望用 fake 模型 + fake 工具 + fake 后端就能判定链路跑通、过滤正确、事件配对，不依赖真实模型、真实沙箱与真实 AK。

## 需求

### REQ-1 开关字段与默认值

`ExecuteKwargs` 新增字段 `tool_use_mode`，取值 `function_call`、`code_mode`，缺省 `function_call`。该字段随既有 `execute_kwargs` 从 ChatCompletion 入参、APIGW 调用、内置插件等链路原样传入，不新增接口与路由。取合法集合以外的值时，请求在参数校验阶段被拒绝（4xx），不装配工具、不执行 Agent、不产生会话消息。

### REQ-2 默认路径零回归

`tool_use_mode` 未传或为 `function_call` 时，装配的工具集合、注入的提示词、产生的 AG-UI 事件序列、审批链路与会话落库结果必须与变更前逐项一致；不新增可测量延迟、不新增事件、不新增日志字段以外的可观测面。

### REQ-3 code mode 下模型可见的工具面

- 模型绑定的工具集合必须只含一个代码执行工具（工具名 `code_execute`），其余已装配工具不再以 JSON Schema 形式注入模型。
- 提示中必须注入由装配结果派生的精简工具清单：每个可调用工具的名称、用途与参数要点；清单必须与代码环境内真实可调用的集合一致（不多不少），被剔除的中断类工具不得出现在清单里。
- 代码执行工具自身不得携带审批配置、不得触发中断，也不得被 `tool_allow` / `tool_deny` / `mode` 之外的条件裁掉。

### REQ-4 代码环境内的工具函数

- 代码环境内为本次装配的每个工具提供同步函数：函数名等于工具名，签名由工具 schema 派生，返回值等于该工具在 function calling 下的执行结果。
- 工具调用必须复用现有工具执行链路（超时控制、结果脱敏、结果截断、MCP 代理、审批包装），与 function calling 共用同一实现，不得另起一套旁路调用。
- 代码环境内可调用的工具集合受 `mode`、`tool_allow`、`tool_deny` 与 code mode 自身约束的共同限制；调用不在集合内的工具名必须以代码内可捕获的异常形式失败，且该工具本体不得被执行。
- 同一段代码内的多次工具调用按代码执行顺序串行；代码可自行做循环、条件分支与结果聚合。

### REQ-5 中断类工具排除与命令级审批处置

- code mode 下，ask 类工具与带生效审批配置的工具不得进入代码环境、不得出现在精简清单、不得被模型以任何形式调用；判定口径复用 `tool-loading-mode` 的 `ASK_TOOL_NAMES` 与 `is_approval_configured`，不新增人工维护的名单。
- code mode 下命令级审批不得发起：`execute` 等工具内落在灰名单的命令按拒绝处理（fail-closed），拒绝结果作为工具结果回到代码，不得创建审批单、不得挂起等待。
- 与 `mode` 叠加时，最终可调用集合必须同时满足两个模式的约束（交集语义）；任一模式剔除的工具都不得出现在模型工具集合或代码环境中。

### REQ-6 执行与上下文回填

- 一轮 code mode 的执行结果回填模型上下文时，只允许新增两段内容：模型产出的代码、代码的执行输出；代码内每次工具调用的入参与结果不得作为独立工具消息、工具调用记录或结果片段进入模型上下文。
- 执行输出超过既有截断阈值时按现有口径截断，并标注截断事实；截断不得吞掉退出状态与错误信息。
- 同一轮内允许多次「写代码 → 执行 → 看输出」的迭代（受 REQ-8 重试上限约束），每次迭代仍只回填该次的代码与输出。

### REQ-7 事件与展示

- 代码内每次工具调用必须产生一对独立的 `TOOL_CALL_START` / `TOOL_CALL_ARGS` / `TOOL_CALL_END` 事件，`tool_call_id` 全局唯一并与该次内层调用一一对应。
- 事件只用于展示与审计，不回填模型上下文（与 REQ-6 一致）。
- 事件类型、字段名与字段语义不得超出基线 AG-UI 集合：不新增 `EventType`，不改既有字段含义，不为内层调用引入「子调用」标记。
- chat-x 渲染链路必须零改动即可显示这些工具调用（含工具名、入参、结果与状态），不出现未知事件告警或渲染错误。

### REQ-8 异常与重试

- 代码语法错误、运行时异常：必须把错误信息回传模型，允许模型修正代码后重试；重试次数上限可配置（默认 3 次），达到上限后本轮必须以失败结果结束，不得静默返回空结果。
- 代码内工具调用失败：必须以代码内可捕获的异常暴露，模型可在代码中捕获处理；未捕获时按上一条的错误回传语义处理。
- 代码执行超时：必须按沙箱统一超时中断执行并回传超时错误（默认沿用 `execute` 的 120 秒，可配置），不得把超时当作空输出成功返回。
- 重试必须重新执行代码，不得复用上一次的部分执行结果，也不得重复已成功的工具副作用之外的重放（同一段代码重复执行导致的重复副作用由调用方在提示层面自行规避，本变更不做幂等保证）。

### REQ-9 运行时覆盖

- `local`、`bubblewrap`、`agent_run`（E2B）、`paas` 四类 runtime 都必须支持 code mode，能力面（工具调用、超时、输出截断、异常回传）一致，不得出现「已配置该 runtime 却无法在 code mode 下执行」的缺口。
- 代码执行的隔离级别、文件可见范围与网络策略必须沿用该 runtime 的现状，不因引入 code mode 而放宽。
- 会话未注册任何可用 runtime 时，按现有工具探测语义处理（无可用运行时，不得伪造本地执行）。

### REQ-10 安全约束

- 代码环境不得获得平台凭据、AK、token 或完整请求体；注入的环境变量按现有 `execute` 的清洗口径处理。
- 代码环境内的可调用工具必须受白名单约束：不得通过导入、反射、或是直接读写宿主进程内部结构调用未装配的工具或绕过审批与脱敏。
- 事件与日志不得输出凭据与 AK；代码正文与工具入参按现有工具调用参数展示口径呈现，不额外扩大暴露面。
- 代码不得获得与本会话运行时范围之外的宿主文件系统访问能力。

### REQ-11 A2A 继承

父 Agent 以 `code_mode` 调用 A2A 子 Agent 时，子 Agent 必须使用同一 `tool_use_mode`；不得回落到 `function_call`，也不得自行升级为其它模式。

### REQ-12 收益测算方案（文档交付）

必须交付《code mode 收益测算方案》，至少覆盖：

- 任务集构成与选取原则：多步工具编排类任务，含 3 次以上工具调用、含循环或条件分支、含结果聚合的场景，以及单步任务（用于观察纯 schema 注入开销）。
- 四项指标口径：prompt token 与 completion token 总量、LLM 请求轮次、端到端耗时、任务成功率；每项必须写清采集点与计算方式。
- 对照方法：同一任务集、同一模型、同一提示预算下 `function_call` 基线与 `code_mode` 的对照，含预热与重复策略。
- 采样与统计口径：样本量、重复次数、去噪方式（模型随机性、缓存命中、沙箱冷启动）。
- 判据：token 节省比例与轮次下降比例的判定阈值、成功率不劣化的容差，作为「是否扩大使用范围」的决策依据。

本期只交付该方案文档；不实现评测代码、不产出实测数据或对比图表。

### REQ-13 契约与兼容

- `tool_use_mode` 为新增可选字段，对 Web、企微、APIGW、内置插件等既有调用方不构成破坏性变更。
- 流式、非流式、resume 续流三条路径在同一 `tool_use_mode` 下装配出的可调用集合必须一致。
- 该参数是请求级参数：不写会话配置、不落库、不影响同一 Agent 的其它并发请求。
- 历史会话续流与 regenerate 路径未携带该字段时按 `function_call` 处理。

## 验收

- ACC-1（REQ-1、REQ-2）当请求未携带 `tool_use_mode` 时，系统必须装配与基线逐项一致的工具集合，并产生与基线逐字节一致的事件序列（同一 fake 模型输入下比对）。
- ACC-2（REQ-2）当请求携带 `tool_use_mode=function_call` 时，系统必须产生与未携带该字段时逐字节一致的事件序列，且工具本体调用次数相同。
- ACC-3（REQ-1）当请求携带合法集合以外的 `tool_use_mode` 值时，系统必须返回参数校验错误（4xx），且装配工具数为 0、会话消息数为 0。
- ACC-4（REQ-3）当请求携带 `tool_use_mode=code_mode` 时，fake 模型收到的 tools 数组必须只含 1 个代码执行工具，且系统提示必须包含精简工具清单，清单中的工具名集合必须等于该会话装配出的可调用工具名集合。
- ACC-5（REQ-4）当 code mode 下模型产出调用两个已装配工具的代码时，两个工具必须各被执行一次、执行顺序与代码一致，且代码能拿到返回值（以 fake 工具的调用计数与返回值断言）。
- ACC-6（REQ-4）当代码调用未装配或被 `tool_deny` 排除的工具名时，代码必须收到可捕获异常，且该工具本体调用次数为 0。
- ACC-7（REQ-5）当会话装配了 ask 类工具与带生效审批配置的工具时，code mode 下的模型工具集合、精简清单与代码环境可调用集合都必须不含这两个工具，且代码调用它们必须失败。
- ACC-8（REQ-5）当 code mode 下代码通过 `execute` 执行一条落在灰名单的命令时，系统必须直接拒绝（fail-closed），审批单创建次数为 0、中断次数为 0，拒绝结果回到代码。
- ACC-9（REQ-5）当同时携带 `mode=dontAsk` 与 `tool_use_mode=code_mode` 时，最终可调用集合必须同时满足两者：ask 类工具与带审批工具都不得出现在模型工具集合或代码环境中，其余工具仍可调用。
- ACC-10（REQ-6）当 code mode 一轮结束后，下一轮模型请求体必须只新增「代码」与「执行输出」两段；内层工具的入参与结果不得以独立工具消息或工具结果块出现（以 fake 模型收到的请求体断言）。
- ACC-11（REQ-7）当代码内发起 2 次工具调用时，事件流必须出现 2 组 `TOOL_CALL_START` / `TOOL_CALL_ARGS` / `TOOL_CALL_END`，`tool_call_id` 两两不同且与外层代码执行工具的 id 不同，事件类型集合不得超出基线集合。
- ACC-12（REQ-7）当用现有 chat-x 渲染上述事件流时，必须正常展示每组工具调用且无未知事件告警；前端目录必须零 diff。
- ACC-13（REQ-8）当模型产出的代码报错时，错误必须回到模型上下文并可触发再次执行；连续失败达到配置上限时本轮必须以失败结束，实际重试次数必须等于配置值。
- ACC-14（REQ-8）当代码执行超过配置超时时，系统必须中断执行并回传超时错误，不得返回空输出或成功状态。
- ACC-15（REQ-9）当分别以 `local`、`bubblewrap`、`agent_run`（E2B）、`paas` 后端执行同一段含工具调用的代码时，四类 runtime 都必须完成工具调用往返并返回执行输出（`local` 与 `bubblewrap` 为真实端到端；E2B 与 paas 以可注入的 fake / 模拟后端断言请求–响应往返契约，具备真实环境时补端到端证据，缺环境时该项记为未取证）。
- ACC-16（REQ-10）当检查代码环境的环境变量与可调用集合时，必须不含平台凭据 / AK，且可调用工具名集合等于装配结果（不多不少）。
- ACC-17（REQ-11）当父 Agent 以 `code_mode` 调用 A2A 子 Agent 时，子 Agent 必须同样只绑定 1 个代码执行工具，且在 code mode 下执行。
- ACC-18（REQ-12）当检查交付物时，必须存在《code mode 收益测算方案》文档且覆盖任务集、四项指标口径、对照方法、采样口径、判据五个部分；本仓不得新增评测代码或实测数据文件。
- ACC-19（REQ-13）当同一 `tool_use_mode=code_mode` 请求分别以流式、非流式与 resume 续流执行时，装配出的可调用工具集合与精简清单必须一致。

## 边界与非功能

- 运行时：Python 3.11–3.12；验收在 Linux x64 容器内完成。代码语言限 Python（沙箱内既有解释器）。
- 兼容性：`tool_use_mode` 为新增可选字段；未传即现状；历史会话、续流、regenerate 均按 `function_call` 处理。
- 性能：`function_call` 路径零额外开销；code mode 单轮至少一次模型往返（写代码）加一次结果回填，代码执行耗时计入端到端；不得为 code mode 在默认路径引入任何常驻进程或监听端口。
- 限额：单次代码执行超时默认 120 秒（可配置）；单次代码内工具调用次数上限默认 50；执行输出截断沿用 `execute` 的 100000 字符口径；重试上限默认 3 次（可配置）。
- 并发：同一会话内的代码执行串行，不同会话互不影响；代码执行不保留跨轮内存状态。
- 安全：沙箱隔离与命令安全校验沿用 runtime 现状，命令级审批在 code mode 下 fail-closed；不新增外网访问能力、不开放隧道、不引入新的凭据下发路径。
- 可观测性：不新增 span 属性与 HTTP 字段；允许在服务端日志记录生效的 `tool_use_mode`、工具调用次数与重试次数，便于排障与后续测算。
- 测试约束：ACC-1～ACC-14、ACC-16～ACC-19 必须可离线运行（fake 模型 + fake 工具 / fake 后端，不依赖外部网络与真实 AK）；ACC-15 的 E2B / paas 真实端到端属取证项，缺环境不影响其余判定。

## 开放问题与假设

- 澄清结论 1（运行时覆盖）：需求方确认 `local` + `agent_run`（E2B）+ `paas` 全部覆盖；`bubblewrap` 作为 `local` 在 `sandbox_policy` 生效时的既有替代实现，按同一抽象一并支持。
- 澄清结论 2（收益评估）：需求方确认本期只需交付收益测算**方案**，不写评测代码、不产出实测数据。
- 澄清结论 3（展示粒度）：需求方确认前端代码不动，代码内每次工具调用按正常的一次工具调用展示。
- 假设 1：开关命名为 `tool_use_mode`（取值 `function_call` / `code_mode`），与兄弟变更的 `mode` 正交、可叠加；若评审要求并入 `mode` 枚举，改动点只在枚举取值与透传，其余需求不变。
- 假设 2：代码执行工具名暂定 `code_execute`；改名不影响需求与验收的判定口径。
- 假设 3：代码内层工具调用产生的事件只用于展示与审计、不回填上下文，这是本变更 token 收益的来源，也是 REQ-6 与 REQ-7 的边界。
- 假设 4：code mode 不承载人工中断，需要人工介入的场景由调用方选择 `function_call`；因此 code mode 下不存在「中断后 resume」的需求。
- 假设 5：兄弟变更 `tool-loading-mode` 尚未合入 `develop`；code mode 的过滤必须自带等价实现（复用 `ASK_TOOL_NAMES` 与 `is_approval_configured` 的同源判定），两分支合入顺序互不阻塞。
- 假设 6：限额默认值（超时 120 秒、单次代码 50 次工具调用、输出截断 100000 字符、重试 3 次）取现有 `execute` 与同类实现的既有口径，评审可调整，调整不改变验收结构。
- 假设 7：code mode 的工具副作用不做幂等与去重保证，重复执行风险由提示层与调用方约束；本期不引入事务或回滚机制。
- 开放问题：无。
