# LLM 装配：Offloading 分层存储需求规格

- 变更名: context-offloading-storage
- 工作分支: feature/context-offloading-storage
- 类型: 功能
- 仓库: git@github.com:ChrisJaunes/bk-aidev-agent.git
- 执行顺序: 无

## 范围

- 新增 SDK 内部「上下文条目（ContextEntry）」数据模型：统一承载十类上下文（含子上下文，以标签区分）的原始数据与元数据（类别、生命周期、来源、标签、状态、版本、时间戳、访问时间）。
- 新增四组存储原语（同步语义）：写入、更新、失效（invalidate）、按过滤器加载；另新增类别注册接口。
- 新增两级分层存储：热层持有活跃条目的 payload 与索引；冷层承载被卸载条目的 payload，热层仅保留元数据与索引。支持闲置卸载、加载时按需回捞、容量淘汰。
- 冷层默认落在进程内存储（LangGraph 会话 state / 进程内存），不引入外置介质依赖；冷层以可替换的后端接口形态存在，本期只实现进程内默认后端。
- 生命周期到期清理能力：提供可调用的到期清理入口（后台周期任务 + 轮次/会话/任务结束回调两条触发路径），本期只交付能力与测试，不挂载到现有装配链路的真实事件上。
- 十类上下文的验证方式：以测试夹具构造样例数据，完成「写入 → 加载 → 卸载 → 还原 → 到期清理」全链路验证；本期不改造任何真实上下文生产方。
- 可观测能力：卸载/回捞/淘汰计数、各层条目数与 token 占用量，以只读统计接口 + 服务端日志暴露。
- 配置项：热层容量上限、冷层容量上限、闲置卸载阈值、到期清理周期，均由环境变量提供并带内置默认值。

## 非目标

- 不改造现有装配链路：`ContextAssembly` 的 tool/template/variable 三条 `MiddlewarePipeline`、`PromptSlots`、`PromptMiddleware` 系列、`chat_history_assembly`、`token_compression` 三层压缩一律零改动；本期不把 system prompt / 工具定义 / 会话历史 / 执行轨迹的真实生产方改为经统一写入接口提交。
- 不实现任何装配策略（全量装配、预算受限装配、压缩替换），不决定条目的组装顺序、截断与格式化；本期只提供读接口与原始条目。
- 不做上下文压缩与 Handoff 替换：不新增摘要产物、不改 `token_compression` 的压缩阈值与策略（由兄弟需求负责）。
- 不做工具延迟加载、工具加载模式、工具 PTC：不定义它们的写入契约，不消费、不修改 `tool_lazy_loading` 的会话态实现。
- 不引入外置介质：不实现本地文件、Redis、数据库等冷层后端；不保证进程重启后冷层条目可还原；不保证多实例/多进程之间共享或还原条目。
- 不新增 HTTP 接口、不新增流式事件类型、不新增 span 属性、不新增请求级参数（`ExecuteKwargs`）。
- 不做 token 估算精度的校准，不做 token 收益的量化验收门槛。
- 不做鉴权与租户校验：隔离只依赖调用方传入的作用域标识（见 REQ-11）。
- 不迁移平台侧（BKAI Agent 配置、State Store、Policy Engine、用户系统）的上下文生产方；这些来源的类别只以样例数据验证。

## 跨仓边界

- 本任务只有一个业务仓 `bk-aidev-agent`（Python SDK），无跨仓接口、无跨仓依赖、无跨仓执行顺序，也不需要平台侧配合。
- 与同仓兄弟需求的边界（均基于 `develop`，互不依赖分支）：
  - 「Handoff：替换当前上下文的压缩方案」：压缩产物如何写入本存储、以何种类别/标签登记，本期不定义；本需求只保证任意类别（含注册的新类别）都能完成写入与加载。
  - 「工具的延迟加载」「工具加载模式」「工具 PTC」：工具定义与工具执行结果的写入形态本期不定义；本需求不修改 `tool_lazy_loading` 相关代码。
  - 原始素材中「数据/接口依赖」表引用的「接口约定」章节在本任务描述中缺失，本期按「不定义兄弟需求契约」处理（见开放问题与假设）。
- 与 `feature/tool-lazy-loading` 分支无代码依赖：本需求从 `develop` 切出，不读取其会话态结构，也不修改其实现。

## 用户故事

- 作为下游装配策略作者，我希望按「类别 + 生命周期 + 标签 + 来源」组合过滤一次拿到原始条目与元数据，自己决定组装顺序与截断，而不必理解各上下文来源的装配逻辑。
- 作为 SDK 维护者，我希望新增上下文类别只做一次注册即可完成「写入 → 加载 → 卸载 → 还原 → 清理」全链路，存储核心代码零修改。
- 作为部署/运维同学，我希望冷层不可用时装配主流程仍能拿到热层数据并收到「数据可能不完整」标志，而不是整体失败；也希望容量与闲置阈值可通过环境变量调整并在取值非法时回落到默认值。

## 需求

### REQ-1 数据模型与必填字段

条目必须具备：`id`（存储分配，全局唯一）、`category`（已注册类别）、`sub_context`/`labels`（子上下文与标签，可为空集合）、`lifecycle`（枚举：平台级 / Agent 级 / 用户级 / 会话级 / 当前轮 / 任务级 / 请求级）、`source`（来源标识）、`payload`（原始数据，可序列化）、`status`（active / offloaded / evicted）、`version`（整数，写入从 1 起）、`created_at`、`updated_at`、`last_accessed_at`。缺失必填字段或取非法枚举值的写入必须被拒绝并返回明确错误。

### REQ-2 写入路径与校验

写入接口接收原始 payload 与元数据；写入前必须校验：类别已注册、必填字段齐全、payload 可序列化。校验失败必须拒绝写入、返回可识别错误，且存储状态（条目、索引、计数）不发生变化。校验通过必须分配 `id` 与 `version=1`，写入热层并更新索引。

### REQ-3 更新与并发冲突

更新接口接收 `id`、调用方持有的 `version` 与新 payload；`version` 与当前一致时递增版本并更新 `updated_at`；不一致时必须返回版本冲突错误并携带当前最新版本，条目内容保持为已提交版本，不得出现字段级部分覆盖。更新成功后该条目必须回到热层（若曾被卸载则先回捞），并按 REQ-6 的策略重新计时。

### REQ-4 失效（invalidate）

失效接口支持按 `id` 或按过滤器批量执行；命中条目 `status` 置为 `evicted`（逻辑删除），后续加载请求不得返回该条目。失效不删除物理数据以外的任何热层/冷层结构信息，也不得影响未命中条目。重复失效同一命中集合必须幂等。

### REQ-5 按过滤器加载

加载接口接收过滤条件（类别、生命周期、标签、来源，任一维度可省略，多维度为「与」关系），返回命中条目的元数据与原始 payload。返回顺序不得被存储内部结构决定为语义顺序（装配顺序由调用方决定）。过滤命中为空时必须返回空结果而非错误。已被失效（`evicted`）条目不得出现在结果中。

### REQ-6 卸载与按需回捞

热层条目在超过配置的闲置阈值（依据 `last_accessed_at`）未被访问时，必须被卸载：payload 序列化迁至冷层，热层仅保留元数据与索引，`status` 置为 `offloaded`。加载请求命中 `offloaded` 条目时，存储必须自动回捞至热层（`status` 回到 `active`、刷新 `last_accessed_at`）并返回完整内容，整个过程对调用方透明，调用方无需额外操作。`offloaded` 条目的元数据必须仍可被过滤器命中（用于统计与容量治理）。

### REQ-7 冷层不可用时降级

冷层后端不可用（读取或写入异常）时，加载接口必须正常返回：仅含热层可服务条目，并附带「数据可能不完整」标志；不得抛出未捕获异常、不得阻塞装配主流程。写入与更新路径必须在冷层不可用时仍成功（仅热层生效）。单条回捞失败必须跳过该条目并记录日志，其余条目照常返回。

### REQ-8 淘汰顺序与永不淘汰约束

热层或冷层超出容量上限时，必须按「淘汰优先级（高者先淘汰），同级按 `last_accessed_at` 最久未用优先」的顺序执行淘汰；淘汰为彻底移除（不可还原），且必须释放对应索引与容量计数。`System Instructions` 类别必须被约束为永不淘汰：在构造满容量压力场景时，其它类别被淘汰后 `System Instructions` 条目仍必须可正常加载。各类别的默认淘汰优先级必须在类别注册表中随类别声明，不得散落在存储核心逻辑内。

### REQ-9 类别注册扩展

类别注册接口必须声明：类别名称、默认生命周期范围、典型来源、默认淘汰优先级、可选 token 预估器；注册后写入与加载接口立即识别该类别，存储核心代码零修改。注册同名类别必须被拒绝并提示已存在。新类别默认继承全局默认策略，注册参数可覆写。

十类内置类别（System Instructions、Agent Definition、Tool Definitions、Skill Context、User Context、Conversation History、Current User Input、Execution Trace、Working State、Environment & Governance）必须以注册项的形式存在，不允许在核心逻辑中硬编码类别分支。

### REQ-10 生命周期到期清理

到期判定：`当前轮` 在轮次结束后、`请求级` 在请求结束后、`会话级` 在会话关闭后、`任务级` 在任务终态后到期；`平台级`/`Agent 级`/`用户级` 不自动到期，只能显式清理。到期条目的处理：热层的先卸载再按淘汰策略决定是否保留；已处于高淘汰优先级的到期条目直接淘汰。仍被活跃任务引用的条目必须延期清理，引用释放后再处理。单条清理失败必须不影响其它条目与主流程，可在下一周期重试；连续失败达到阈值必须输出告警。清理入口必须可由调用方显式触发（供测试与轮次结束回调使用），并支持配置周期。

### REQ-11 作用域隔离与并发安全

条目必须按调用方传入的作用域标识隔离（会话级隔离；不同会话的加载结果互不可见），禁止使用进程级或模块级全局可变状态作为条目唯一容器。同一存储实例被并发调用（多线程与 asyncio 协程）时，写入/更新/加载/失效必须不产生数据竞争、不抛出未捕获异常；并发写入不得丢失已成功提交的条目。

### REQ-12 配置项

新增环境变量（命名沿用 `BKAI_` 前缀与 `config.py` 的 `env.*` 注册方式）至少覆盖：热层容量上限（条目数）、冷层容量上限（条目数）、闲置卸载阈值（秒）、到期清理周期（秒）。未设置时使用内置默认值；取值非法（非整数、小于 1）时必须回落默认值并输出告警日志，不得导致 Agent 构建或导入失败。配置随进程启动读取生效，不支持运行时热更新。

### REQ-13 十类样例数据与全链路可测

必须提供测试夹具，为十类类别各写入至少一条样例条目（其中 `Working State` 与 `Environment & Governance` 各覆盖至少两个子上下文标签），并驱动全链路：写入 → 按过滤器加载 → 卸载 → 回捞 → 到期清理。夹具必须位于既有测试目录结构内，不进入生产代码路径。

### REQ-14 可观测

必须提供只读统计接口，返回：热层条目数、冷层条目数、各类别条目数、卸载次数、回捞次数、淘汰次数、token 占用量估算。卸载、回捞、淘汰、降级、到期清理必须写入服务端日志（含条目 id、类别、原因）。不得新增流式事件类型，不得新增 span 属性。

### REQ-15 测试覆盖

上述行为必须有单元测试覆盖：必填字段与非法类别拒绝、可序列化校验、版本冲突、失效幂等、多维度过滤器、卸载阈值边界、回捞透明性、冷层不可用降级、淘汰顺序与 `System Instructions` 永不淘汰、类别注册与重名拒绝、到期清理与引用延期、配置非法回落、并发写入、十类样例全链路。

### REQ-16 现有装配链路零回归

本期改动必须以「新增模块 + 新增配置项 + 新增测试」为限：不得修改 `ContextAssembly`、`PromptSlots`、`PromptMiddleware` 系列、`chat_history_assembly`、`token_compression` 的函数签名与运行行为，不得在现有装配链路中插入任何调用；在相同输入下，现有 prompt 装配结果（system/human 槽位、工具列表、chat_history 变量）必须与变更前逐项一致。

## 验收

- AC-1：当为十类上下文（含子上下文以标签区分）各写入一条样例数据并经加载接口读回时，系统必须返回与原始提交一致的 payload、类别、生命周期与来源。
- AC-2：当提交缺少任一必填字段或类别未注册的条目时，系统必须拒绝写入并返回明确错误，且条目总数、索引与统计计数保持不变。
- AC-3：当提交的 payload 不可序列化时，系统必须拒绝写入并返回错误，且存储中不出现该条目的任何痕迹。
- AC-4：当以「仅当前轮 + 会话级」与「含 Agent 级 Tool Definitions」两个过滤器分别加载时，系统必须分别返回各自对应子集，无遗漏、无多余条目。
- AC-5：当条目超过闲置阈值被卸载后，系统必须使热层不再持有其 payload（`status=offloaded` 且热层条目数下降），随后的加载请求仍必须取回完整内容并将其还原为 `active`。
- AC-6：当模拟冷层不可用时，系统必须让加载接口正常返回（仅热层条目 + 完整性标志），且写入与更新请求仍然成功。
- AC-7：当注册一个全新类别后，系统必须使该类别可完成「写入 → 加载 → 卸载 → 还原 → 到期清理」全链路，且存储核心代码无需修改。
- AC-8：当注册与既有类别同名的类别时，系统必须拒绝注册并提示已存在，且既有类别行为不变。
- AC-9：当两个调用方基于同一 `version` 并发更新同一条目时，后提交者必须收到版本冲突错误并拿到当前版本，最终条目内容必须为最先提交者的版本。
- AC-10：当轮次结束后触发到期清理时，`当前轮` 的 `Execution Trace` 条目必须按策略被清理或淘汰；仍被活跃任务引用的 `任务级` 条目必须不被清理。
- AC-11：当构造热层容量压力场景时，系统的淘汰顺序必须符合「淘汰优先级 + LRU」，且 `System Instructions` 条目在全过程中必须始终可正常加载。
- AC-12：当对同一命中集合重复调用失效时，系统必须保持幂等（条目只被标记一次，后续加载持续不返回）。
- AC-13：当两个不同会话使用同一存储实例时，一个会话写入的条目必须不出现在另一会话的加载结果中。
- AC-14：当多线程与 asyncio 协程并发写入 N 条条目后，系统必须使 N 条条目全部可被加载，且无未捕获异常。
- AC-15：当环境变量取非法值（0、-1、非整数）时，系统必须回落内置默认值并输出告警日志，且模块导入与存储初始化成功。
- AC-16：当调用只读统计接口时，系统必须返回热层/冷层条目数、各类别条目数、卸载/回捞/淘汰次数与 token 占用量估算，且该数据不改变任何存储状态。
- AC-17：当执行 REQ-16 的零回归验收时，`ContextAssembly`、`PromptSlots`、`PromptMiddleware` 系列、`chat_history_assembly`、`token_compression` 的既有单元测试必须全部通过，且相同输入下的 prompt 装配结果与变更前逐项一致。

## 边界与非功能

- 兼容性：新增独立模块与配置项，不改变现有模块的函数签名与行为；不新增 HTTP 字段与流式事件，存量调用方零感知。
- 性能（参考目标，非阻塞验收）：热层命中加载 P95 < 50ms（千级条目规模）；进程内冷层回捞 P95 < 500ms；热层写入 ≥ 1000 条/秒。实测值记入交付说明，不设失败阈值。
- 并发：同一实例的读写必须线程安全与协程安全；不得用模块级全局可变状态承载条目。
- 内存与容量：热层与冷层均受配置上限约束；超限必须触发淘汰，禁止无界增长。
- 降级：冷层异常只降低能力（热层数据 + 完整性标志），不中断调用；降级路径必须可观测。
- 正确性优先于吞吐：卸载/淘汰/回捞不得丢失 `active` 条目的 payload；`offloaded` 条目被淘汰时按彻底移除处理并计数。
- 可维护性：类别、生命周期、淘汰优先级、token 估算口径均由注册表声明；核心存储代码不得出现「按类别名分支」的逻辑。
- 可测试性：闲置阈值、容量上限、到期判定必须可注入时钟或可显式触发，禁止依赖真实 sleep 才能验证。

## 开放问题与假设

- 已确认（2026-10-26）：本期只交付存储底座与十类样例数据测试，现有装配链路（system prompt / 工具定义 / 会话历史 / 执行轨迹）零改动（选项 A）。
- 已确认（2026-10-26）：冷层先放进程内 state 即可，不要求落本地文件或 Redis，也不要求进程重启后还原、不要求多实例共享。
