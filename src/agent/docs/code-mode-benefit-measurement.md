# code mode 收益测算方案

- 变更名：tool-ptc-code-mode
- 对应需求：REQ-12
- 适用范围：`bk-aidev-agent` 的 `ExecuteKwargs.tool_use_mode`（`function_call` / `code_mode`）
- 本文档只定义测算方法，不含评测代码与任何实测数据

## 1. 任务集构成与选取原则

### 1.1 选取原则

- **同源可比**：基线与 code mode 使用同一任务集、同一模型、同一提示预算、同一工具集合（除 `tool_use_mode` 外无差异）。
- **覆盖两段收益**：既要有「工具 schema 常驻注入」的固定开销样本，也要有「多轮调用-结果回填」的随步数增长的开销样本。
- **可判定**：每个任务都有程序化可校验的完成条件（返回值 / 产物 / 状态），不依赖人工主观打分。
- **可控副作用**：任务只使用幂等的读写类工具或可回放的假服务，避免重复执行造成不可逆写入。

### 1.2 任务分层

| 分层 | 构造 | 工具调用次数 | 观察目标 |
| :--- | :--- | :--- | :--- |
| S1 单步任务 | 单次读取 / 单次查询 | 1 | 纯 schema 注入开销（code mode 的固定成本是否可被覆盖） |
| S2 多步直排 | 3–5 次串行工具调用 | 3–5 | 上下文回填的线性膨胀 |
| S3 含循环 | 对被检索结果集逐条处理（≥3 条） | 3–10 | 编排逻辑从「多轮决策」迁移到代码后的轮次下降 |
| S4 含条件分支 | 按前一步结果选择不同工具路径 | 3–6 | 分支决策的稳定性与轮次收益 |
| S5 含结果聚合 | 多次查询后汇总、去重、排序 | 4–8 | 内层结果不进上下文带来的 token 节省上限 |
| S6 失败恢复 | 首次代码报错后修正重试 | 2–4（含失败轮） | 重试机制的开销与成功率影响 |

每层建议 8–12 个任务，总样本量 50–70 个任务；同一任务在两种模式下各跑相同次数。

## 2. 四项指标口径

### 2.1 token 消耗

- **采集点**：每次 LLM 请求的 usage（`prompt_tokens` / `completion_tokens`），在模型网关或 SDK 的 usage 回调处按 `session_code + turn_id` 累加。
- **计算方式**：
  - 单任务 token = Σ（该任务全部 LLM 请求的 `prompt_tokens`）+ Σ（`completion_tokens`）；
  - 分别报告「prompt token 总量」「completion token 总量」「合计」三项；
  - 节省比例 = `(基线合计 - code mode 合计) / 基线合计 × 100%`。
- **归因拆分**：另记录每次请求的 messages 条数与 system prompt 字符数，用于区分「schema 注入下降」与「历史回填下降」两部分贡献（二者之和应能解释大部分差异）。

### 2.2 LLM 请求轮次

- **采集点**：单任务内完成的 LLM 请求次数（以一次 `invoke`/`stream` 完成计 1 次，重试不计入轮次但单独统计）。
- **计算方式**：单任务轮次 = 请求计数；聚合用中位数与均值并列，避免长尾误导。
- **下降比例** = `(基线轮次中位数 - code mode 轮次中位数) / 基线轮次中位数 × 100%`。

### 2.3 端到端耗时

- **采集点**：从任务开始执行到产出最终答案的时间戳差，含 LLM 请求、代码执行、沙箱文件往返与工具执行；不含评测框架的准备与清理。
- **计算方式**：单任务耗时取多次重复的 P50 与 P90；分别报告「纯 LLM 耗时」与「工具/沙箱耗时」，用于解释 code mode 的固定成本（沙箱启动、每次内层调用一次轮询往返）。
- **注意**：`local` / `bubblewrap` 的沙箱开销近似为 0；`agent_run` / `paas` 需单独列出冷启动时间，不与热执行混算。

### 2.4 任务成功率

- **采集点**：任务结束后的程序化校验结果（期望产物 / 返回值 / 状态断言）。
- **计算方式**：成功率 = 通过任务数 / 总任务数；同时记录「因代码执行失败重试耗尽而终止」的比例。
- **容差**：成功率是最硬的判据，任何 token 收益都不应以成功率的显著下降为代价。

## 3. 对照方法

### 3.1 分组

- **A 组（基线）**：`tool_use_mode=function_call`（缺省）。
- **B 组（实验）**：`tool_use_mode=code_mode`。
- 其余参数完全一致：同一模型与温度、同一 `mode` / `tool_allow` / `tool_deny`、同一系统提示主体（code mode 追加的精简清单不视为提示预算差异，需在报告中单独说明其字符数）。

### 3.2 执行顺序与预热

1. 每组先跑 2 个任务做预热（丢弃结果），覆盖模型侧缓存与沙箱冷启动；
2. 预热后按「A-B-B-A」交错执行，抵消时间漂移（模型网关限流、机器负载）；
3. 每个任务重复 N 次（建议 N=5），A/B 各得 N 个样本。

### 3.3 变量控制

- 关闭或固定模型侧 prompt 缓存，避免缓存命中差异污染 token 统计；
- 固定沙箱镜像与 runtime 类型；跨 runtime 比较时按 runtime 分层报告，不做跨 runtime 合并；
- 工具实现使用可回放的假服务，保证两次运行输入相同。

## 4. 采样与统计口径

- **样本量**：每层 8–12 个任务 × 每任务 5 次重复；总有效样本 ≥ 500 次单任务执行。
- **去噪**：
  - 模型随机性：固定温度与随机种子（若供应商支持）；不支持时用重复取中位数；
  - 缓存：关闭 prompt 缓存与工具结果缓存（本变更不含 code mode 结果缓存）；
  - 沙箱冷启动：单独标记首次执行样本，统计时剔除或单列。
- **异常值**：耗时用 P50/P90 而非均值；token 与轮次用中位数与 IQR 描述；超过 3×IQR 的样本标记为异常并单列，不直接删除。
- **显著性**：对成功率使用两比例检验（α=0.05）；对 token / 轮次 / 耗时的配对差值使用 Wilcoxon 符号秩检验，报告效应量与置信区间。

## 5. 判据

以「是否扩大 code mode 使用范围」为决策目标，建议判据：

| 维度 | 扩大使用（推荐） | 观察 / 限定场景 | 不扩大 |
| :--- | :--- | :--- | :--- |
| token 节省 | 合计节省 ≥ 25%，且 S2–S5 每层均 ≥ 20% | 合计节省 10%–25% | < 10% 或部分层为负 |
| 轮次下降 | S2–S5 轮次中位数下降 ≥ 40% | 下降 20%–40% | < 20% |
| 端到端耗时 | P50 不劣于基线 10% 以内 | 劣化 10%–30%（仅限长任务） | 劣化 > 30% |
| 任务成功率 | 不劣于基线（差值 ≤ 2 个百分点，且检验不显著） | 劣化 2–5 个百分点 | 劣化 > 5 个百分点或失败集中在单层 |

决策规则：

1. 四项同时满足「扩大使用」→ 在无人值守的多步编排场景默认启用；
2. 成功率满足、其余部分满足 → 只在 S3–S5（多步 / 循环 / 聚合）场景启用；
3. 成功率不达标 → 不扩大，先定位代码执行与重试语义问题；
4. 单步任务（S1）若 token 收益为负，属预期（code mode 有固定成本），不据此否决整体结论，但需在报告中单列。
